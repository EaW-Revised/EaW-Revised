# Walk 28: land unit abilities

## Scope and evidence

This walk catalogues every ability kind that the effective XML gives to a land object
and records the engine rules behind each: how it is switched on and off, what gates it,
its targeting, duration and cooldown, what it does, and how it interacts with stealth,
Force disabling, formations, healing and hazards. It covers the two ability layers
that land objects use:

- **Unit abilities**: the `Unit_Abilities_Data` / `Unit_Ability` entries (`Type` is one
  of 75 authorable kind names) that put a button on the command bar.
- **Nested handlers**: the `Abilities` children (`*_Ability` tags with an
  `Activation_Style`) that carry the effect. A unit ability reaches a handler through its
  `GUI_Activated_Ability_Name`; a handler can also run on its own (automatic, damage- or
  targeting-triggered).

Boundaries: [abilities](abilities.md) and [space abilities](../space-abilities.md) own
the shared framework (switch, expiration countdown, recharge, multipliers, autofire);
[heroes](heroes.md) owns the special-ability service kernel (WHE-09 to WHE-14) and hero
identity; [land combat](land-combat.md) owns terrain, garrison and capture;
[land AI](land-ai.md) owns plan selection; [build pads](build-pads.md) owns the healing
handler's space and structure rules (WSH). This walk adds the land kinds and the land
branches of the shared kinds; it does not repeat a rule it can cite.

Sources are the **debug build** (read-only inspection), the **effective XML**
(`DLAB-nn` snapshots below) and existing sourced walks. Opaque evidence IDs `ELAB-01` to
`ELAB-65` identify inspections; their private notes, the address map and the XML
catalogue tooling remain in ignored `out/research/land-abilities/`. No retail capture
was made, so every number is either a code constant (said so) or an authored XML value
(said so); authored values are not universal defaults. A rule that rests on a reading the
inspection did not finish says **unverified** and is listed in the last section.

## Entry points and service order

A land ability starts from one of four places: a command-bar or hotkey switch, a Lua
`Activate_Ability`, an autofire or AI trigger, or an automatic handler service. The
unit-level switch checks the kind, the unit's own ability data and the enabled gate
(WLAB-06), then branches by kind (WLAB-10, WLAB-11 and the kind rules). A modal kind then
puts the slot itself on or off. Handlers run in the special-ability service kernel of the
owning object (WHE-09 to WHE-14), which the frame-order walk places in the object's
ability tail. The rule table follows that dependency: framework and gates, unit-level
kinds, then the nested handlers, then shared helpers, AI and presentation.
