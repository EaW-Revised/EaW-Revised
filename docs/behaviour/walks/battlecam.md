# Space battle cinematic camera walk

Research for (legacy EAWR-3005). This is a read-only debug-build walk; evidence IDs map to a private address ledger. Values below are engine coordinates or logical frames, not pixels. The galactic tour is out of scope. Existing scheduling rules WBF-16, WBF-26 and WBF-28 apply. **Unverified** marks a gap, not a retail rule.

| BCAM-01 | Default battlecam binding is Space; C is a distinct unit-preview command, not the default battlecam binding. The owner's 'C' most likely refers to the interactive unit-preview view used for close inspection; the default map binds Space to battlecam and C to preview, while capture confirmed Space, and an owner or remapped-key check is pending. | BCAM-06 | The general pool starts with objects having locomotion behavior; types must allow `Movie_Object`, have a mode model and not have the Wall category. | BCAM-07 | The interest score combines normalized model-bounds size, combat power, position relative to the candidate mean, health, target activity and displacement, weighted by the seven `Saliency_*` constants. Lower health is favored by the normalization. The candidate set affects the normalization. The list sorts by descending score. Let K be the smaller of 10 and candidate count minus one: it makes K attempts, each drawing an inclusive index from 0 through K, seeking both a different object and a different type; if unsuccessful it takes index 0. Hardpoint choice tries random live hardpoints with a cinematic target. | debug build BCAM-E04/E05/E18; stock `gameconstants.xml` |
| BCAM-08 | An object-attached key resolves the object by ID; when it no longer exists, the position resolver tries a cached attachment position. Selection validates the saved object ID before choosing another. If a single camera key or a cut key cannot resolve its attachment or cache, it uses the last camera or target position respectively. These render lookups do not themselves advance the shot; the normal expiry path chooses the next one, validating the saved object first. Death and removal need not coincide, so the precise visible death-to-removal transition still needs capture. | debug build BCAM-E04/E12/E15/E21/E25 |
| BCAM-09 | Shot selection first attempts a type's authored glory sequence, then a selected hardpoint shot. Fighter category attempts chase. Otherwise there is a random floating-shot attempt, followed by category-specific choices: bomber/corvette can try frigate or chase, frigate tries frigate, and remaining cases ultimately choose circle or flyby. Some land and generic fallbacks also exist; no fixed ship-name list should replace this dispatch. | debug build BCAM-E06; capture BCAM-E27 |
| BCAM-10 | Chase uses the length R of the cinematic model-box half extents (world bounds when the model is absent for a team), so distance scales down with small subjects. A random angle is in either 135..225 or -45..45 degrees. One variant starts at radial 6R and longitudinal 3..7R, ending at radial 6R and 2..9R with the same random side, over 2..4 seconds; the other uses radial 3R and travels longitudinally from -6..-8R to +2..+4R over 4 seconds. Both target the object origin and add drift and spiral effects. In one fighter capture, repeated chase initializations appeared roughly 2.3 to 4.1 seconds apart in the debug log. | debug build BCAM-E07; capture BCAM-E24/E27 |
| BCAM-11 | **Decompile only, not observed:** the circle geometry and timing, and the numeric flyby geometry below; the capture logged a capital flyby but did not measure these values. Circle uses object half-extent length R: its initial sideways distance is ±2R, height 1.25 times the vertical half extent, with random orbit direction and frequency 600 logical frames. Duration is `(90 + floor(180*smoothstep(30,500,R))) / logical FPS`. Here x, y and z are the cinematic model-box half-extents in model space, before transformation; R is their vector length. Logical FPS is 30 in the stock schedule (FC-76); keep the divisor explicit. For implementation until the helper is independently checked, use clamped Hermite smoothstep: let t = clamp((R-30)/(500-30), 0, 1), then smoothstep(30,500,R) = t*t*(3-2*t); this is a provisional interpretation, not a measured curve. Regular flyby uses bounds-scaled endpoints `(2x, ±2y, 2z)` and `(2x, ∓2y, 2z)`, rotated by the model transform, over `3 + 4*smoothstep(30,500,R)` seconds. The space belly variant travels from `(0,-0.6y,-z)` to `(0,3y,-1.5z)` over `8*(1+smoothstep(30,500,R))` seconds. The checked flyby excludes two stock hull types from its belly variant. This outline does not apply those name-specific exceptions; their compatibility behavior needs capture before implementation. | debug build BCAM-E08; capture BCAM-E27; FC-76 |
| BCAM-12 | **Decompile only, not observed:** the hardpoint and frigate parameters in this row. The hardpoint view anchors the camera at offset `(0,0,200)` in the hardpoint weapon-orientation frame, with a 90-degree Z rotation applied to that orientation and translation to the hardpoint position; it aims at the hardpoint target, lasts a random 120..180 logical frames, and can choose automatic FOV. The target is rejected when fogged, hidden or below its opacity threshold. The frigate path constructs bounds-scaled endpoints and can transfer its view to an attack target over 180..240 frames; when its geometric target conditions fail, that initializer returns failure and selection continues. | debug build BCAM-E09/E15 |
| BCAM-13 | **Decompile only, not observed:** the numeric floating-shot parameters and the glory path below. A bomber floating-shot initializer appeared in the debug log; its framing and timing were not measured. Floating shots choose a random azimuth and 20..45 degree elevation, optionally below in space, at 2..4 times the half-extent length from a fixed world-space target, for 60 logical frames. A glory shot chooses a `Glory_Cinematics` entry, loads its authored cinematic file and attaches its camera and target keys to the subject; its duration is the largest key frame. A missing or unreadable file falls through to another shot. The `.tec` file format is not documented by this walk. | debug build BCAM-E10; capture BCAM-E27 |
| BCAM-14 | Without FOV keys the camera uses the tactical controller FOV, or 55 degrees when unavailable. Hardpoint auto-FOV uses a size/distance angle and can insert eased keys, clamped to 25..55 degrees. The checked separate framing helper computes `atan(R / D)` in degrees, where R is the target model-box half-extent length and D is camera-to-target distance; the auto-FOV caller doubles an angle before applying its clamp, but its intermediate calculation has not been traced, so do not treat `2*atan(R/D)` as a verified auto-FOV formula. The missing calculation needs a binary trace, and direct FOV measurement needs capture. Authored FOV keys and their easing override the default. Camera and target position keys use spline, linear and cut paths, with rotation available for the camera; shot endpoints above should not be interpreted as a crossfade between subjects. Until those curves are verified, use the sourced spline for position keys marked spline, linear interpolation for linear keys, a direct cut for cut keys and a direct cut when replacing a shot; where the spline is unavailable, use linear interpolation as an explicitly provisional fallback. Exact visual cut and interpolation curves need capture. | debug build BCAM-E11; BCAM-E08/E09 |
| BCAM-15 | The manager services the playing shot only when `In_Game_Cinematics` is enabled. Shot expiry advances movie mode unless the current scene is held or Tab is down. If the next movie shot cannot be initialized, cinematic mode ends. Shot initialization replaces the prior key set; the bars have their own transitions. The path uses a dedicated cinematic random stream: a local 32-bit linear congruential generator. It is seeded from a high-resolution timer at process startup. Its use is local presentation state and must not draw from the simulation RNG; the checked references do not prove identical camera sequences across peers. | debug build BCAM-E12/E13/E23 |

| BCAM-18 | The generic dispatch also has building and flying initializers. The building path uses a bounds-scaled moving camera and an optional target, with 60..90 frame segments. | BCAM-19 | C preview chooses the hovered possible unit first, otherwise the selected unit, and requires local ownership. In space it starts at 30 degrees elevation with distance clamped to 3..10 times the model-box half-extent length. Repeated C steps through eight azimuths in 45-degree increments; pointer motion and wheel adjust the view. | BCAM-20 | An authored cinematic file uses little-endian chunks: each has a 32-bit ID and length, whose high bit marks a group. Top-level groups 0, 1 and 2 hold camera-position, target-position and FOV keys. Position keys use chunk ID 4; value keys use ID 5. Their microchunks carry one-byte ID and length: 0 is the 32-bit frame, 3 the 32-bit transition, 10 the three-float attachment offset, 9 the float value, and 11/12 the outgoing/incoming ease fractions. Transition 2 holds the first key until the cut; otherwise interpolation uses the ease curve. For ease fractions a and b, the normalized path integrates a linearly rising velocity over a, constant velocity through the middle, and a linearly falling velocity over b. Spline-position evaluation remains provisional linear fallback under BCAM-14; roll and shake keys need separate implementation. | debug build cinematic and key readers, ease helper; BCAM-E10/E11 |
| BCAM-21 | The hardpoint weapon orientation used by BCAM-12 is constructed from the world-space X axis of the current first fire-bone transform; the anchor is the hardpoint's transformed world position. | debug build hardpoint orientation and position readers; BCAM-E09/E15 |
| BCAM-22 | A frigate transfer requires an attack target with a model, a heading differing by more than 80 degrees, and a target direction within 30 degrees of the subject's facing. It uses two 90..120-frame segments. Let m be max(x,z) of the subject half-extents. Its opening offset has X and Z independently scaled by random integers 1..7 times m and sine/cosine of one random angle, and Y scaled by 5..10. The middle offset uses subject X and Z with a second angle, and the midpoint of two independently selected signed Y offsets; the final offset attaches to the target at `(0,-1.5y,2z)`. The checked random angles convert the integer degree draw to radians twice. Both position paths use the BCAM-14 spline fallback until its curve is implemented. | debug build BCAM-E09 and facing comparison |

The effective stock `gameconstants.xml` weights size, power, health and speed at 1; X and Y at 0.5; targets at 1.5. `Movie_Object` is a per-type eligibility flag, default true (BCAM-E20). `Glory_Cinematics` lists authored `.tec` sequences, for example in `spaceunitscapital.xml` and `uniqueunits.xml`. The checked selection and shot paths do not establish a per-unit battlecam offset tag or a general camera table; absence has not been proved across the complete binary. Types may also author `SFXEvent_Engine_Cinematic_Focus_Loop` (for example in `uniqueunits.xml`); preview focus switches the unit engine loop for both automatic shots and unit preview (BCAM-E22/E25). Story Lua camera keys are a separate interface, not evidence that battlecam reads them.

BCAM-09's floating attempt draws an inclusive integer in 0..3 and attempts the shot on zero. For bomber or corvette, a subsequent 0..1 draw chooses frigate on zero and chase on one; the final circle/flyby choice also uses an inclusive 0..1 draw (BCAM-E06).
For the BCAM-11 belly variant, the target key is attached at model-space offset `(0, -6y, 0)` (BCAM-E08).

For BCAM-07, the size input is the squared length of the bounds half-extents, speed is displacement since the previous position, and targets count incoming and outgoing attack-object and cinematic-hardpoint targets. For each input, compute its candidate minimum, maximum and mean; use 1 as the divisor for a zero range. Size, power, targets and speed use `(value - minimum) / range`, X and Y use `1 - abs(value - mean) / range`, and health uses `1 - (value - minimum) / range`. For each normalized input, multiply every candidate's value by the range of that input's normalized values, then sum the seven weighted values. These are debug-build rules (BCAM-E05), not a claim that every input is currently published by the viewer.

## Implementation outline and open work

Replace the `AttractCamera` seam in `apps/viewer/src/attract_camera.hpp` and its `map_mode_live.cpp` caller with a presentation-only controller that consumes immutable battle snapshots, bounds and relevant authored type data. Route remappable battlecam input and the tactical button through the same state machine; save and restore tactical camera and UI state, and keep presentation randomness outside simulation and replay state. Load saliency weights, eligibility and glory references through normal data paths. Preserve subject identity safely across destruction. Do not implement the unverified multiplayer rule or unexplained attract discrepancy as proven retail behavior.

Tests should cover candidate filtering and ranking with synthetic data, selected-subject opening, eligible attack-target shortcut, repeat avoidance, missing models and dying subjects, per-category shot selection, scaling from fighter to capital, FOV/key evaluation, input hold/release and UI restoration, deterministic simulation hashes with camera enabled, and attract startup failure. Test both empty and modified authored lists.

Capture cases and remaining coverage (the entry/exit and ship-shot cases were approved; no multiplayer or attract captures were run):

1. **BCAM-01..04:** two debug sessions confirmed Space, letterbox and HUD suppression; the later session also showed Escape restoring the HUD. The first recorder failed before its later checks, so remapped key, C preview, hold/release, button, small and large mouse movement, click, other controls during battlecam, and bar restoration remain capture-needed.
2. **BCAM-05..08:** selected fighter, mixed owner and fogged candidates, active attack, no eligible target, and subject death or removal during a shot.
3. **BCAM-09..14:** one debug log recorded the selected corvette starting chase and the selected capital falling through from a frigate attempt to flyby. The video started after those initial short shots; a later capital flyby and fighter/bomber shots appear in the sequence, with bomber chase and floating initializations in the log. The separate bomber staging request was refused before execution. Direct FOV measurement, the initial corvette shot on video, and unobserved circle, hardpoint, successful frigate and authored glory paths remain capture-needed.
4. **BCAM-15..16:** held Space and Tab at expiry, paused entry and expiry, speed changes, and two-player multiplayer availability and pacing.
5. **BCAM-17:** menu attract startup on a populated map; record whether movie initialization succeeds and whether the rendered camera changes, then compare with the prior static trace.
6. **BCAM-10:** trace or capture chase axis assignment and the drift and spiral parameters; the initial implementation uses a provisional model-frame axis assignment and disables those effects.
7. **BCAM-19:** capture the initial preview distance and pointer sensitivity; the initial implementation uses 3R and a provisional motion scale within the sourced distance clamp.
8. **BCAM-13/20:** authored roll, shake and exact spline-position keys still need implementation and capture; unsupported or malformed files fall through.
9. **BCAM-12:** attached-model fire bones and hardpoint auto-FOV still need implementation; unsupported initializers fall through to the documented category fallback. Squad/team frigate targets and the transfer's exact spline curve also need coverage.
