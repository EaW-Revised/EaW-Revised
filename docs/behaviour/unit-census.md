# Obtainable FoC space-skirmish units and mechanic coverage

Station upgrades unlock production; they do not supply the combat and lifecycle
handlers of the new units. Ships and fighters can reuse existing movement,
weapons, shield, energy and squadron services, but their authored abilities,
special weapons, hero identities and construction paths still need consumers.
This census records fidelity needs rather than asserting that an untested unit
works. The later headless unit matrix, contact sheets and debugger-driven retail
duels remain separate validation work.

## Census contract

- **UC-01 — acquisition scope.** Enumerate the multiplayer menus of all fifteen
  `Skirmish_{Rebel,Empire,Underworld}_Star_Base_[1..5]` types, the three factions'
  `Space_Skirmish_AI_Default_Forces`, and the capture-producer menus documented
  by WBP-01/WBP-33/WBP-34. Include the additional authored
  `Skirmish_Hutt_Asteroid_Base` capture producer conservatively; this census does
  not establish its presence on a selected map. Follow completed mines' own
  upgrade menus. A type without a purchase button can still be obtained as a
  launched reserve, a team member, a constructed child or an ability spawn;
  these routes are explicit, not invented reinforcement menu entries.
- **UC-02 — effective definitions.** Read the installed game through the existing
  offline inventory VFS, `tools/inventory/corpus.py#read_effective`, using FoC
  override priority and active registry includes. Case-fold names and resolve
  `Variant_Of_Existing_Type`. Object winners follow layer, registry and definition
  order (`src/data/xml_registry.cpp#index_winners`); list values come from the
  closest authored variant layer (`src/units/unit_support.cpp#Object::list`),
  with repeated scalar occurrences retained as evidence. Keep top-level object
  identities separate from nested ability names. Nine Underworld station upgrades
  and two Underworld mining upgrades
  collide with their nested ability names in the runtime's global lookup;
  this is an explicit missing mechanic, not permission to census an ability
  definition as a purchased ship or upgrade object.
- **UC-03 — support evidence.** Join each authored class/tag pair to
  `docs/tag-coverage/statuses.json`, retain its status, application location,
  rules and missing kinds, and group related inputs within their tracking area.
  A cited application is support for that consumer, not proof of an entire
  object's fidelity. `applied` becomes implemented only with code evidence;
  `partial` is projected onto the affected unit kind; `todo` is missing where a
  walk establishes space consumption. A todo input without a space-consumption
  rule stays unknown rather than inflating the confirmed blocker count. Keep
  ignored and deferred scope decisions in `excluded_tags`, rather than turning
  them into blocking mechanics. Manual handler judgments cite the supported
  dispatch (`src/sim/tactical/abilities.cpp#kind_names`), the ability table and
  the walks. Untraced service details stay unknown. The reviewed code fingerprints
  in `data/census/mechanic-review.json` cover named handler functions/regions,
  bounded by unique literal anchors and normalized to LF. Edits outside those
  regions do not invalidate the review. A changed region, missing or ambiguous
  anchor stops both generation and checking, naming the moved fingerprints and
  the exact regenerate command; known gaps are never refreshed as unknown.
  Re-review the changed consumers and registry/walk evidence before updating
  fingerprints or generated files. New support paths must be added to the
  reviewed regions as part of that review. No gameplay rule
  is implemented by this inventory.
- **UC-04 — dependency closure.** Follow squadron craft, team containers,
  carrier start/reserve lists for an opted-in `SPAWN_SQUADRON`, construction
  results and ability-spawned objects. Preserve craft multiplicities and signed
  reserve counts. Inspect object weapons, every authored hardpoint and their
  projectile profiles, including unit-ability projectile overrides and inherited
  hardpoint `Blast_Ability_Fire_Projectile_Type` charged shots (EWW-03,
  WHE-35/WHE-36, WWP-14/WWP-26). These special profiles contribute the same
  downstream mechanic requirements as ordinary shots. Ordinary
  shot projectiles live in the weapon definitions; independently spawned bombs
  and effects are also roster objects. Death clones and presentation assets are
  outside this simulation census. A starting/reserve list without the spawning
  behaviour is metadata, not a claimed launch route.
- **UC-05 — honest uncertainty.** HeroCompany ground abilities do not become
  space abilities (WHE-05). Follow both company-transport and member unique-space
  relationships as **deployment candidates**; WHE U-02 leaves the actual
  conversion policy unverified, notably Vader's differing transport and unique
  craft. Carrier/team dependencies must preserve their own authored abilities
  and timers. Stock space mines are excluded by WHZ-60: the examined stock maps
  have no minefields and the stock placement ability is land-specific. Modded
  mine services, the untraced bomb/lure/self-destruct cleanup branches and
  black-market-dependent stealth policy need additional evidence. No Ghidra
  lookup or gameplay change was necessary to assign these honest statuses.
- **UC-06 — ranking and validation.** Count unique affected object IDs, then
  separately count affected acquisition roots. Propagate each mechanic's
  per-unit support state through deployed/launched/spawned dependencies; keep
  source menus separate, so a station does not inherit every optional purchase's
  combat needs. One object's missing mechanic can affect its squadron and carrier
  without representing three purchases. Fix-order counts overlap and are not
  additive. Refresh/check JSON and the generated tables together.

## Refresh and machine interface

`data/census/space-units.json` is schema version 1. `units` contains acquisition
routes, faction reachability, authored tech/base restrictions, cost, category,
behaviours, locomotors, unit and special abilities, dependency edges and special
tags. `weapon_definitions` stores shared hardpoint/projectile profiles by ID;
each unit's `weapons` references them. `need_status` is direct support and
`need_status_including_dependencies` is the closure to use for the later
validation matrix. `mechanics` provides fix order, evidence and affected units.
`inputs` hashes the active registry XML without embedding installation paths or
retail assets. Never infer purchase entitlement from a category, filename,
galactic tech field or the mere existence of a type.

Set `EAWR_EAW_GAME_ROOT` to the installation root, then run:

```text
python tools/inventory/unit_census.py --docs docs/behaviour/unit-census.md --issues-out out/unit-census/proposed-issues.md
python tools/inventory/unit_census.py --check --docs docs/behaviour/unit-census.md
python tools/inventory/tag_registry.py check
```

CTest `unit_census_game_data` runs the sync check and skips with return code 77
when the game-root environment variable is absent. The generator contracts run
in `inventory_contracts`. Handler support must be reviewed again after station
upgrade integration; updating a fingerprint alone does not establish support.
The proposals remain ignored local reports for coordinator triage, with existing
tracking ownership identified for reuse.

Blocked objects include each direct user and any acquisition root or container that depends on it; each object is counted once per mechanic.
