# Galactic selection and paid build consumers

The galactic engine accepts an immutable, target-local selection provider. Its
complete flag qualifies the whole supplied generation: authored plan constraints,
ordinary and magic admission, original type metrics, population, terrain, hero
weights, learned survival, distinct ground/space target and escort contrast,
whole-object freestore identity, and producer reach/travel facts. Missing or
incomplete generations refuse selection; an empty plan registration is insufficient.
The stock-content adapter and full authored plan materialization remain explicit
integration seams in this first consumer piece.

Selection commits authored proposal/team order and synchronized choices while D
partitions immutable score and producer contributions (WGA-58..60/66). Ordinary
build sources use real producer identities; freestore uses whole owned objects,
including retained transit waits (WGA-29/77). Tactical reinforcement pools do not
supply galactic requests. Time admission compares linear selected build duration
and D's concurrent queue estimate; the goal time limit constrains funding instead
of replacing that duration test (WGA-20/21).

Completed proposal passes reevaluate category funding before active desire,
category ordering and reservation maintenance (WGA-75). The retained funding owner
reserves capital and income, with separate feasibility and activation queries
(WGA-21..23). Reservation leaves the world account unchanged. Global exclusions
register once and release once, preserving zero-valued rows (WGA-57).

Paid execution retains the actual admitted build identity and waits for an ordered
producer outcome. The producer reports completion only after authoritative
creation, with the exact resulting original actor. Cancellation reports failure
after queue removal. These outcomes are saved in the production contributor's
version-seven component. Manual cancellation refunds its serviced paid fraction;
automatic producer loss retains that spend (WGEP-46/64/67). Completed work retains residual marks. Goal removal selects salvage before teardown,
releases capital plus accumulated income to the category, and transfers only selected
remaining cost to the aggregate dead budget (WGA-348/349); orphan bills consume that budget.

The synthetic runtime contract exercises selection, reserve, attachment, paid
admission and exact completion on 1/2/4/8 workers, including native restore during
reservation. It is supporting proof, not installed Normal stock behavior. Native
paid/magic/cash journal integration and active disk-save replay remain unproven
until the second piece composes the stock provider and R2 journal.

## Live task publication and staging

The owning engine publishes WGA-347/354 rows from retained TaskForce/plan/player,
requested type, associated producer/channel and actual build identity. The typed economy
reader matches recorded builder and head build, as well as type and location. Completion
cost, spendable funding and budget duration remain goal fields. Task remaining cost uses
the selected channel head's stored price and sampled progress instead. Head countdown
reads the current world frame, independently of that sampled progress (WGA-343/344).
Creation, association, completion, salvage, removal and restore invalidate a separate
derived task revision; clock-only barriers do not scan the task roster.

Fresh funding uses the exact authored time limit sentinel and computed proposal budget;
allocation and release preserve negative unallocated values and never refund accounts
(WGA-345/346). A finished goal can still retain its Potential; reservation lifetime and
actor return must follow that retained identity, rather than the finished flag. Actual
production results retain their outer fleet identity, while roster assignment resolves
the first direct member and keeps a company or squadron shell intact (WGA-350).

The target-local staging reader derives authored force stages without recursively calling
the selector. It consumes qualified native garrison/combat-skip and source-planet
usability readers, then applies BTP-S01..03's helper and aggregate arithmetic. These
world flags have one saved world owner; the engine stores neither duplicate flags nor
guessed birth defaults. Missing readers remain BTP-U04. The retail team-definition
index archive remains BTP-U02; this implementation makes no closure claim for it.

Build-budget publication returns shared immutable DTO storage. Its derived cache keys the task-specific
revision, funding revision and production-specific NativeActions build_state_revision. Cache hits
reuse storage without allocation; movement/freestore-only writes cannot dirty this publication.

## Automatic ground-preference landing seam

WGA-405..416 source the native single-actor landing consumer behind
WGA-31/90. The retained actor's current transport behavior, immediate parent
and literal grandparent, stored ground preference, live safety/surface/capacity
and movement-block state must come from their authoritative owners. The
configured `Max_Ground_Forces_On_Planet` remains data-driven. Cargo ground
capability, original-type planet restriction and stock hero destination-helper
preference are separate readers, not automatic-landing gates.

Bind native service before freestore Lua main/unit work at the existing admitted
execution boundary (GFS-A04/11). Assignment can consume the actor first;
reservation alone does not skip native landing. Retire finished movement state
before transit admission, then commit direct single-actor removal before landing
with live capacity revalidation under ADR-009. Preserve the stored preference
across representation, return and restore; missing providers remain unavailable.
Issued events and a formation-land notification do not prove successful surface
containment. Ordinary fleet landing/invasion is a separate action owner.

The static implementation checklist and proposed capacity/preference/refusal
cases are in the [automatic landing walk](walks/gc-ai.md#automatic-ground-preference-landing).
GAL-U01 retains actual first arrival/return/load service, indirect preference
writes and callback/tie qualification within the existing frame/restore programme.
