# Space tactical super weapon (the Death Star)

The object with the `TACTICAL_SUPER_WEAPON` space behaviour (stock `Death_Star`, inherited by `Death_Star_II`; mods rename it
freely, so the type is found by the behaviour, never by name) runs one state machine, serviced every logical frame (service
interval 1, 30 frames per second). It has no locomotor and no pathfinding: its position is set directly. The sequence has two
parts. The first is the approach up to and including the ready phase and the command that drives it (TSW-01..TSW-07: the
approach, the ETA, the gate). The second is the fire sequence (TSW-08..TSW-12): power-up, the attack, the destruction of the
target prop, the debris and the post wait, the battle's victory hold and the planet fact handed to the galactic side.
The script calls that drive it from a tactical script (TSW-14) are a thin client of the same command. Presentation (sound,
music, the power-up cinematic, the attack clip, the explosion, the debris props) is published as events and consumed
by the viewer (TSW-15); the simulation draws and plays nothing.

Evidence: "debug build" is a read-only walk of the FoC debug build (2026-11-13); "XML" is the stock data read in place.
"Played run" is the debug-build run recorded in space-tactical-superweapon-walks.md (rule ids TSW-W.. and TSW-C..). The attacker
case (the approach and its readout) and the frame-resolution view of the explosion are not captured yet (legacy EAWR-6941). Numbers
below that are derived from XML are marked.

## States (our names)

| State | Name | Entered when | Left when |
|---|---|---|---|
| S0 | idle | object creation | the approach is begun |
| S1 | facing | approach begun | the object has turned to its target |
| S2 | approaching | facing done | distance to the target is at or below `TSW_Attack_Distance_From_Target` |
| S3 | ready | range reached, or a defending owner's first service | power-up accepted |
| S4 | powering up | power-up accepted | the power-up countdown reaches zero |
| S5 | charged | S4 ends | the next frame |
| S6 | attack start | the frame after S5 | the same frame (the attack animation countdown is loaded) |
| S7 | attack animation | S6 | the attack animation countdown reaches zero |
| S8 | target destruction | S7 ends | the same frame (the target and the planet go) |
| S9 | debris wait | S8 | the debris delay reaches zero (the debris is created) |
| S10 | post wait | S9 ends | the post-destruction wait reaches zero |
| S11 | complete | S10 ends | the next frame: back to idle (S0), target cleared, hold released |

## Rules

| Rule | Behaviour | Evidence |
|---|---|---|
| TSW-01 | Placement at first service: start or attack distance from the nearest enemy target, heading toward the battlefield centre. | See galactic-space-entry.md (TSW-01), rig capture 2026-10-16. |
| TSW-02 | Data. The behaviour's numbers come from the object's own XML: `TSW_Attack_Distance_From_Target`, `Max_Speed`, `Max_Thrust` (approach), and the four sequence timings `TSW_Power_Up_Countdown_Seconds` and `TSW_Attack_Anim_Duration_Seconds` (seconds, multiplied by 30 and truncated to whole frames), `TSW_Explosion_Debris_Creation_Frame_Delay` and `TSW_Post_Destruction_Wait_Frames` (frames). An absent tag is zero (the type constructor leaves each at zero; only `TSW_Start_Pos_Match_Targets_Z` defaults to on), so a mod object without the data does nothing harmful: with no `Max_Speed` it never moves. The remake keeps one record per object in the tactical state (state, first-service flag, target, speed, countdown, announced speech thresholds); a battle without such an object carries and saves nothing extra. | Debug build (type constructor and tag table); XML. |
| TSW-03 | First service (once per object). The object then picks its target: the nearest `DUMMY_TACTICAL_SUPER_WEAPON_TARGET` prop not owned by its own faction (the TSW-01 rule; ties go to the lower map record: unverified, it only matters at equal distance). With no target it only faces the battlefield and stays idle. With a target, an owner that DEFENDS the conflict starts in S3 (already placed at the attack distance); every other owner starts the approach at once (S0 to S1): no player click is needed, so in a normal attack the Death Star flies in by itself and the player's first click is the fire click. A skirmish has no defender. The first service is the object's first tick in the session. | Debug build. |
| TSW-04 | Gate, both requests. A request is refused unless the conflict exists, its planet exists and is not destroyed, and the planet's type allows destruction by the super weapon (`Planet_Is_Destroyable_By_TSW`; stock authors No on three planets). A skirmish has no parent conflict, so a skirmish Death Star never fires. The first-service approach of TSW-03 is not a request and is not gated. The conflict inputs are carried in the battle setup (target list and gate). Until the galactic side supplies the planet facts the campaign entry sets "destroyable, standing" (TODO (legacy EAWR-6952)); a planet type that does not author the tag is destroyable (the type constructor's default is yes, debug build; only the stock planets that author No refuse), so the unauthored default is yes. | Debug build (request path); XML. |
| TSW-05 | Approach (S1, S2) and ready (S3). S1 is one frame: an instant full 3D facing from the object to its target (heading and elevation, no roll), then straight to S2; there is no turn rate and no stop condition. (A slow turn exists in the debug build only behind a script-enabled "face the super laser target" flag, default off and unused in stock battles; it is not modelled.) S2, each frame: if the distance to the target is at or below `TSW_Attack_Distance_From_Target`, measured before that frame's move, the object is in range and moves to S3 (it does not move that frame); otherwise its speed rises by `Max_Thrust` (starting from 0, capped at `Max_Speed`) and its position advances that far along the line to the target, set directly (no collision, no locomotor). S3 slows the speed by `Max_Thrust` per frame to zero and the object still moves that far along the same line while the speed is above zero; it does not turn or re-face in S2 or S3 (the heading is the one S1 set). A defender, or an object with no target, only has the placement's yaw-only facing toward the battlefield centre (TSW-01). All arithmetic is fixed-point; the visible result is the retail one to within a frame of position (fidelity list). | Debug build (facing, in-range test, deceleration); XML numbers (stock Death Star: start 8000, attack 5800, `Max_Speed` 0.75, `Max_Thrust` 0.02 per frame: about 98 s from the start, including a 38-frame ramp; derived, not captured). |
| TSW-06 | ETA and speech. The ETA is the distance still to fly to the attack distance over `Max_Speed`, in frames (zero when in range; a type with no `Max_Speed` never arrives and has no ETA). The approach announces 60, 30, 15 and 5 seconds before arrival, once each, in that order (the speech lines are the faction's own; the remake emits a presentation event per threshold with the own-or-enemy choice left to the viewer), then the move into range. The threshold check only runs while the speed equals `Max_Speed` and the range is not reached (debug build walk), so the thrust ramp announces nothing; a threshold already passed by then (a short approach, or a long ramp) is announced on the first frame at cruise speed. None of these events changes the simulation state. | Debug build (thresholds and event order); derived (frame conversion). |
| TSW-07 | Command. One command, the super weapon switch (replay opcode 37, order kind `tactical_superweapon`), lists the one object and a stage: `start_approach` (idle to facing) or `start_power_up` (ready to powering up, TSW-08). It is validated at execution on every peer: the object is live, the issuer owns it (and, under controller policy, controls it), the object has the behaviour, the gate is open and the stage matches the state; an accepted approach request picks its target as the first service does (a request that finds none is refused), and a request made before the first service is the first service for an attacker (or a skirmish object), while a defender's object that has had no first service yet is already ready by TSW-03, so its approach request is refused. A refused request leaves the state alone and publishes `order_rejected`. A `start_power_up` request on an object that is not ready, or once the planet is destroyed, is refused. The script call uses the same command with the AI admission flag (never accepted from a human packet: the human ingress of every battle kind - the tactical lockstep adapter that carries skirmish and LAN seat input, and the campaign and galactic routes - refuses it before it reaches the session). Human click and script call therefore give the same simulation effect and the same replay bytes. | Debug build (click handler, event check at execution). |
| TSW-08 | Power-up, attack start, attack animation (S4..S7). Accepting `start_power_up` on a ready object (TSW-07) starts S4: the countdown is `TSW_Power_Up_Countdown_Seconds` in frames (TSW-02), the speed is set to zero (the object stops where it is: unverified, the debug build's S4 service was not read for a slowing run; at most a few tens of units on a 5800-unit stand-off), the battle's victory hold goes up by one (TSW-09), and the sequence publishes `tsw_power_up_started` (the presentation plays the activation voice and power-up sound, starts the activation music mode and the cinematic: the played runs saw the cinematic start in the click's command frame, TSW-C4). The accept frame counts as the first countdown frame: a countdown of N frames ends N-1 frames later. A timed state lowers its countdown by one each frame and moves on in the frame it reaches zero (a zero countdown moves on in its first frame); S5 lasts one frame; S6 loads `TSW_Attack_Anim_Duration_Seconds` in frames, re-applies the instant facing of TSW-05 (the debug build applies it again at this frame) and publishes `tsw_attack_started` (the attack clip and fire sound), and S7 counts the animation down. From the request tick E the stock numbers (270 / 75 / 33 / 350 frames) give: attack start E+271, destruction E+347, debris E+380, post wait over E+730, back to idle E+731. The played runs saw the battle music resume about 570 frames after the command, longer than these timings (the cinematic or the post wait may define it: unverified, a presentation matter). | Debug build (state functions, countdown loads); XML numbers; played run TSW-C4. |
| TSW-09 | Victory hold. A battle-wide counter, the hold, goes up by one at S4 and down by one when S11 returns the object to idle. While it is above zero the battle's victory tests are deferred: a destruction that would decide the battle (a counted star base, a unit count, the campaign leader or station test) is recorded, in order, with the owner and the object, and decides nothing yet; the star base and unit lists are updated as always. When the hold reaches zero the recorded tests run again, in the order recorded, against the state at that moment, and the list is dropped; the first test that finds a winner decides the battle with that frame as the deciding tick (the pending-victory countdown of VT-11 runs from it). A victory already decided before the power-up stands: the hold defers tests, it does not cancel a decided result. The battle itself goes on during the whole sequence, and after it: the sequence ends nothing by itself (played runs: three minutes later the ships were still fighting, TSW-C5). An object destroyed during S4..S11 ends its sequence and releases its hold at once (unverified: the debug build's handling of an object lost mid-sequence was not walked; the alternative would leave the battle undecidable). Nothing is dropped and there is no cap: a unit or star base test reads only the loser's owner and the state at the release, so the list keeps one such entry per owner (the first, which names the deciding unit; a second one would repeat its answer), and every leader or station entry is kept (each entity is destroyed once, so they are few). With two objects in sequence the hold counts both and the tests run when the last one ends. | Debug build (the monitor's wait counter and its retest); played run TSW-C5. |
| TSW-10 | Destruction, debris and the planet fact (S8, S9). S8 destroys the target prop and then its planet in one frame: the target is recorded as destroyed (it never qualifies as a target again), the planet is recorded as destroyed in the battle (the gate of TSW-04 shuts for every later request), and the tick publishes `tsw_target_destroyed` (the presentation removes the prop, picks one of the type's death explosions with its own non-synchronised random stream, plays the death sound as a plain event and shakes the camera: TSW-W4) and, in the same frame, `planet_obliterated`. `planet_obliterated` is the hand-off the galactic side consumes exactly once per battle: only the destruction that flips the planet fact publishes it, so a second object whose sequence was already running (two super weapons) still ends its own sequence and publishes its own `tsw_target_destroyed` and `tsw_debris_created` (target-keyed, so a consumer keys on the target index) but not a second hand-off. It carries the object, its owner and the target index, not the planet: the galactic side resolves the planet from the battle's conflict record; the galactic side runs the leader-kill victory test of TSW-W5, requests the planet's ruins once, and reads the same fact from the battle result (`planet_destroyed`, set from the battle's planet fact, saved with the result). S9 counts `TSW_Explosion_Debris_Creation_Frame_Delay` frames, then publishes `tsw_debris_created`: the presentation creates the target type's `Death_By_TSW_Replacements` objects for the neutral player at the target's pose (the placement record in the battle setup). Debris objects are decoration and are not simulation objects. The destruction happens at the destruction frame, not at the end of the battle. | Debug build (destruction step, tag table, battle-end result); XML (stock prop types); TSW-W4, TSW-W5. |
| TSW-11 | Post wait and complete (S10, S11). S10 counts `TSW_Post_Destruction_Wait_Frames`; S11 returns the object to idle with no target, publishes `tsw_sequence_complete` and releases the victory hold (TSW-09). A second sequence cannot start in the same battle: the planet is destroyed, so the gate (TSW-04) is shut. Whether the switch resets after the sequence is not settled (the played runs disagree, TSW-C3); the simulation exposes only the object's state. | Debug build (state functions); played run TSW-C3. |
| TSW-12 | State, hash, checkpoint and replay. The fire sequence adds no replay bytes: its only input is the `start_power_up` stage of the switch command (TSW-07). The object's record (TSW-02) gains the phases S4..S11 and their countdown. The battle carries one more block, only with a super weapon setup: the hold, the planet fact, the destroyed targets (ascending) and the recorded victory tests; it is saved with the records, hashed with them (the TSWS block, version 2) and checked on load (the hold equals the number of records in S4..S11, a sequence record has a target and no speed, destroyed targets are listed and in range, a recorded test needs a hold, and a unit test is recorded at most once per owner). A battle without a super weapon setup carries and hashes nothing extra. The tick's events are presentation and hand-off facts and are not part of the state hash. The sequence is serviced serially for the same reason as the approach (a handful of objects, ordered side effects on the victory state). | Project rule (determinism); see TSW-02. |
| TSW-13 | The switch view (presentation). Each snapshot carries one row per object with the behaviour, ascending entity id, for the Death Star switch (HCB-47): the object, its owner, its phase, whether it has been serviced and has a target, the TSW-04 gate including the battle's own planet fact (TSW-10), and the ETA to arrival (TSW-06: zero when ready, none while idle or in the sequence, computed from the object's position while it is facing or approaching, so the row carries one in the facing phase too). The rows copy committed state; they are not part of the snapshot's canonical bytes and move no hash. The presenter uses the first row, whoever owns it: the switch shows while any such object exists, is enabled only for its owner while it is ready and the sequence has not been fired, and its press sends the TSW-07 power-up request (the stage is the object's next one; the switch is disabled in every other phase, so the approach stage is never sent from the button). The press is accepted locally by the same admission the simulation uses (phase and gate, TSW-07): accepted plays the object's `TSW_SFXEvent_GUI_Bttton_Press` event, refused plays the generic GUI negative-feedback event; a disabled switch and a switch of another owner do nothing. The readout shows ` %03d.%03d` (seconds, thousandths of a second) while the object is approaching or ready with a target and the switch has not been fired: green approaching, red ready. Evidence: TSW-W7/W8 and the played runs TSW-C2/C3. Unverified, least-visible choices: which tooltip key shows when (too far before ready, the ready text while ready and after the click, as the played run showed no change, TSW-C3), the readout's colours and offset, the second field being thousandths, the evil-faction condition (any faction shows it), the switch's reset after the sequence (it stays down), and the lever going down on the first snapshot that shows the sequence running (retail latches on any click, so a refused click leaves the retail switch down but ours usable). | Debug build (switch update and click routines); played runs TSW-C2, TSW-C3; project rule for the snapshot rows. |
| TSW-14 | Script calls. A tactical script reaches the machine through three calls; the stock space plan that fires the Death Star uses all three. `Find_First_Object(type_name)` is a global: the first live object whose current type matches the name (ASCII case-insensitive), whoever owns it. Our order is ascending object identity, which is creation order (the retail active-object order is unverified); the answer is nil when no live object matches or the name is unknown, a missing or non-string first argument is a script error, and further arguments are ignored. `Is_Tactical_Superweapon_Ready()` is true exactly in the ready phase (S3); it looks at neither the gate nor the owner. `Fire_Tactical_Superweapon()` takes no arguments (extra ones are ignored) and answers true when the object is ready and the gate is open (TSW-04); it then stages the shared switch command of TSW-07 (power-up stage, AI admission, issuer the object's owner, whoever runs the script) and answers false otherwise. Both methods are a script error on an object whose type lacks the behaviour; a behaviour the battle holds no setup for (a battle without the super weapon setup) is inert: never ready, never fires. The command applies at the next tick boundary, where the validator checks the same facts again; retail runs the transition inside the call, and the stock plan sleeps after it, so the one-tick delay is not observable by that plan (fidelity list). A second call for the same object by the same script instance in the same tick answers false and stages nothing; a second instance that asks in the same tick stages its own request, and the validator refuses the later one by TSW-07 (the phase has moved on). Stock plan on installed data: the plan does not fly the object: it approaches by TSW-03, the plan waits for the ready phase and the parent's `Want_To_Fire_DS` equation, fires once, and ends after its sleep. | Debug build (the three calls, 2026-11-13 walk); mounted stock plan read in place; tests `foc_ai_contracts`, `foc_ai_tsw_plan_stock`. |
| TSW-15 | Presentation consumers (the viewer; nothing here feeds the simulation or a hash). Each sim event of the sequence has one consumer. **Speech** (the approach events, TSW-06): the line is read from the LOCAL player's faction, never the object owner's: `SpeechEvent_Super_Weapon_Moving_Into_Range` at the approach start, `..._Moving_Range_60/30/15/05_Seconds` at the threshold crossings and `..._Moved_Into_Range` at the arrival; the phrase is the own one when the object's owner is the local player or on its team, and the `..._Enemy_...` form otherwise; a faction without the tag stays silent. Lines queue as ordinary speech. **Power-up** (`tsw_power_up_started`): the object's `TSW_SFXEvent_Activate_Voice` and `TSW_SFXEvent_Weapon_Power_Up` play as plain events (not positional) and `TSW_MusicEvent_Activation_Start` starts the tactical music's super weapon mode (BA-46); the cinematic camera is a separate ticket. **Attack** (`tsw_attack_started`): the object's own `SFXEvent_Fire` plays at its position (read from the object itself: the stock super weapon has no projectile, hardpoint or weapon tag, so no weapon-keyed fire sound exists for it) and the model's attack clip starts at its first frame; the clip is `<model stem>_attack_00` over the idle clip, played at its own rate and held on its last frame until the destruction frame (`tsw_target_destroyed` ends it). The clip index is **unverified**: no XML tag selects it (the super laser's own handler has such a tag, this behaviour has none), and every stock super weapon model that has an attack clip has an index 0 one, so index 0 is the least visible choice. **Destruction** (`tsw_target_destroyed`, the 1-based target index names the prop): the prop stops being drawn, the prop type's `Death_SFXEvent_Start_Die` plays as a plain event (TSW-W4), and one entry of its `Death_Explosions` list starts as a particle effect at the prop's recorded position and yaw, the entry picked by a random stream local to the viewer (never the simulation's; seeded from the target and the tick so a replayed view repeats itself); a type with no explosion destroys silently. A target prop that the environment view draws (the stock planet backdrops) is dropped from that view's snapshot, so the rest of the scene is untouched; a target that is an ordinary scene prop is not hidden yet (fidelity list). **Debris** (`tsw_debris_created`): the target type's `Death_By_TSW_Replacements` types, listed by the same function the destroyed-planet battle start uses (WGT-57/101), are drawn as neutral props at the recorded position and yaw for the rest of the battle; they are prepared hidden at battle start, so no model loads mid-battle. The XML has no separate debris tag: the replacements are the debris. `tsw_sequence_complete` has no consumer. Only a battle with a super weapon setup prepares any of this. | Debug build (TSW-W4, played run TSW-C4); XML (faction speech and music tags, the object's TSW_ tags, the prop tags). |
| TSW-16 | Power-up cinematic camera (presentation). The sequence's `tsw_power_up_started` event starts a cinematic in the frame the power-up is accepted (played runs: the command's execution frame, TSW-C4; the event is read after the frame's ticks and before the frame is drawn, so the first drawn frame already shows the shot): the camera cuts to a close shot of the object's dish, the battle UI and fog overlay hide like the other campaign cinematics', the selection and any armed order clear (the selection is not restored afterwards, as with the arrival cinematic), world input is dropped (no skip), the pointer shows its normal look, and the battle is paced at 30 frames per second whatever the speed step; pause still pauses (unverified: checked by reading only, the presented tick stops). In a multiplayer battle, or one with an agreed pace, the pacing request is refused as for the other cinematics, so the shot runs at the agreed pace and its 570 ticks take correspondingly less or more wall-clock time. A second power-up that arrives during a shot (a second object) gets no shot of its own, and the first shot is not replayed. The shot is a pure function of the frame since the event, the dish's position and firing direction and the model radius (`tsw_camera`): the dish is where the line from the model's centre to its first fire bone meets the hull, firing along that bone's forward axis (stock Death Star models: the bone is an emitter point about a tenth of the radius above the hull, about 24 degrees above the equator trench, so the shot aims at the hull point below it: the line from the object's position through the bone, cut at the hull radius of the drawn model (the pick box's, which matched the drawn silhouette; the model's raw mesh bounds are about a tenth larger); the axis is the object's facing once the sequence has pointed it at the target; a model without such a bone falls back to its surface along the object's facing), the camera stands 1.4 model radii from it (estimated from the played run's still, where the sphere runs off the frame edge with the dish bowl about 175 by 240 pixels in a 1280 by 720 window; unverified, an earlier 1.9 left the whole sphere in frame), 45 degrees off the axis on the side that puts the dish on the left of the picture and the sphere running off to the right (the one still of the shot); the eye's height above the dish is the axis' own rise scaled by cos 45 degrees, so the shot is level with the dish only for a horizontal axis; near and far planes are the arrival cinematic's (1 and 10000). The shot is held for the whole cinematic: 570 frames from the event, after which the player's camera and the UI return at once (the played runs measured 571 and 568 frames to the battle music resuming with the camera and HUD back; the data's own comment on the post-destruction wait puts the activation music at 19.15 s = 575 frames). The object must be drawn: an object the local view does not draw (fogged, no model) plays no cinematic. The camera never touches the simulation: no state, no hash, no replay byte. Unverified, least-visible choices (each a constant or a gate in one place): that the first fire bone is the dish the debug build frames (its pose was not read), the bearing, distance and level of the shot (taken from one still at the cinematic's start), whether the camera moves at all (the shot is held; the played runs only have stills), whether the camera cuts to the target for the attack and explosion within the 570 frames, whether letter-box bands show (the one still shows none; the existing bands slide in over the first frames), whether the player can skip it (input is dropped, as in the arrival cinematic), whether a Death Star the local player does not own plays it (it does, when drawn), and whether the length is the music's or the camera's own. The explosion's camera jitter (TSW-W4) and the music, speech and sounds belong to the presentation of the events (TSW-15). The geometry is covered by the `camera_tsw_contracts` test; the viewer lifecycle (start, hide, end, return of the player's camera and UI) is verified by eye on a lit clip only, with no automated viewer test. | Played runs TSW-C4 (cinematic start frame, close dish shot, about 570 frames, HUD hidden); XML (`spaceunitssupers.xml`, comment on the post-destruction wait); tests `camera_tsw_contracts`. |
