### First-service gates and skirmish versus campaign

Stock `gamescoring.lua` calls the shared base definitions, which clear
`LastService`, and authors `ServiceRate = 10` seconds. Scoring rereads both
globals each visit. A numeric rate with no numeric stamp admits a pump
immediately; with a numeric stamp it requires synchronized elapsed seconds
minus that stamp **strictly greater** than the rate. A continuing pump writes
the current synchronized time afterward. Missing/nonnumeric rate skips it.
The stock `main` reaches `GameService` before its event pump. This first-pump
exception is why the stock ten-second rate is not an initial ten-second delay.

Fresh-game default-player creation resets/re-attaches scoring unless the
reset is explicitly suppressed. A GC child transition retains the parent
game and its synchronization clock. The scoring start callback distinguishes
fresh skirmish statistics from campaign tactical statistics; it does **not**
clear `LastService` or restart `main`. Consequently a retained scoring instance
need not pump on f, even though its service visit still precedes AI. A saved
game or deliberately suppressed reset must not be treated as a fresh instance.
Authored scripts remain free to change these globals or call `Suspend_AI`.

The capture wrapper in `tools/validation/p1_capture/foc_capture_mod.py` changes
the rate in its base-definition hook. Its tactical start hook resets staging
and records space mode; the ordinary suspension is in
`EaWR_Stage_Service` in `tools/validation/p1_capture/staging_probe.lua`, called
from the recurring `GameService` wrapper. It is not a suspension in the start
callback. With a fresh, unpumped scoring instance and a suspension-enabled
scenario, that first scoring pump can suspend before the player pass on f.
With an already pumped instance the rate gate can defer it. A later debugger
attachment alone establishes neither case. `Suspend_AI(1)` disables processing
for all modes; `Suspend_AI(0)` enables that global gate, subject to the
independent mode gate. It does not rewind goals, reservations or clocks.

## Interface

Inputs are command admission order and owner, synchronization and gameplay
frame numbers, object service registration, authored `Behavior` and
`SpaceBehavior`, modifier duration, ability countdown state and population
registration. Outputs are command effects, retained modifiers and targets,
new objects and released population. Frame t means the frame being serviced;
it is not automatically the remake's completed-tick counter.

The [frame-order walk](walks/frame-order.md) supplies the containing schedule:
commands before mode service, grid decay before objects, synchronized objects
before presentation objects, and each manager's delayed creations before its
deletion flush. Objects follow most recent service registration first;
periodic behaviours follow attachment order. These are nested object turns,
not universal movement, damage and firing phases.
