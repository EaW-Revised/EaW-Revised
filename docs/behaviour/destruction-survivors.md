# Destruction survivors in space

This note covers `SpaceUnit` and space-mode `SpecialStructure` sources. The rules below were checked in the debug build. Land sources, `SecondaryStructure`, and other object classes keep their separate coverage gaps.

| Rule | Behaviour | Evidence |
| --- | --- | --- |
| DS-01 | `Destruction_Survivors` contains type/weight pairs. An empty list produces nothing. An independent uniform admission draw rejects an attempt below one minus the total weight. Admitted attempts then sample the weighted list. Weights below a total of one retain their no-spawn probability; totals above one do not create extra attempts. A selected type that cannot place a model produces nothing, without redistributing its weight. | debug build, weighted selection and destruction consumer |
| DS-02 | `Minimum_Destruction_Survivor_Count` and `Maximum_Destruction_Survivor_Count` default to one. The signed inclusive helper swaps reversed bounds, consumes no draw for equal bounds, and caps the sampled width at 32766 above the lower endpoint. Nonpositive resulting counts make no attempts. Each attempt selects independently. This is a width limit, not a cap on authored endpoints. | debug build, type defaults, destruction consumer and signed random helper |
| DS-03 | Ordinary eligible destruction requires survivor production to be allowed, excludes pending deletion and death clones, and uses the separate vehicle-thief ejection branch when that ability exists. The enclosing predicate admits tactical modes, including space, rather than requiring a skirmish session. There is no extra render-fog gate. | debug build, common destruction consumer and mode predicates |
| DS-04 | Start with the source's current owner. If its faction is not affiliated with the selected type, choose the first affiliated player in stored player order. With no match, retain the source owner. | debug build, destruction consumer |
| DS-05 | Ordinary company placement creates one body or expands the authored space members. The first successfully created member's `Create_Team` decides whether to form teams; `Max_Squad_Size` partitions them. Types without a model for this mode fail placement. Placement receives the source facing, then each physical body is teleported to the source position, including every member of a formed team. | debug build, company placement and destruction consumer |
| DS-06 | This company call disables population registration, elevated arrival vulnerability and reinforced-garrison registration. It has no reinforcement-pool or population-cap admission. This rule does not assert that every unrelated lower-level creation hook is population-free. | debug build, destruction call arguments and company expansion |
| DS-07 | Each created company receives a coordinated move. Distance is the first `Spawned_Squadron_Location_Flyout_Distances` value, otherwise the planar length of the source world bound extent. Direction is the first `Spawned_Squadron_Location_Bones` bone axis when available; otherwise a free-space point near the source supplies a normalized direction. A second free-space search qualifies the destination. Both searches use distance 1000 and starting angle zero. No source velocity copy occurs in this consumer. | debug build, destruction consumer |
| DS-08 | Survivor creation precedes the later destruction endpoint. Render fog is not an admission gate. Visibility publication and first native periodic service are not established by this local call trace. | debug build, destruction consumer |
| DS-T1 | Approved implementation seam: actual bodies and creation defaults are staged during the ordered destruction hook, and their victory relevance is registered before the source removal can decide the battle. They join the ordinary body/craft/mind rosters after periodic services, with first services on the next tick. Exact native frame order remains a frame-service-map follow-up; this is not a claim about that order. | owner-approved seam |
| DS-09 | Presentation prepares reusable body slots for the survivor's affiliation-selected owner, including non-lobby owners and physical company members. Preparation follows the source and prepared arrival types through survivor chains at load time, with a bounded per-owner/type warm prefix. A cached owner/type admission permits later growth when this prefix is exhausted or disabled. It does not require or add reinforcement arrival, population or garrison flags. | project presentation bridge; DS-02/04/05/06; survivor warm and slot fixtures |

The implementation uses the existing transactional world random stream in destruction order. Its generator is the remake's generator; the sourced count bounds and probability rules remain independent of the generator. A request exceeding the session resource limit fails the tick instead of silently substituting a smaller count. Failed creation leaves committed state and publication unchanged.

The current simulation exposes ordinary destruction and quiet removal; quiet removal does not request survivors. Presentation death clones are not admitted as tactical units. The vehicle-thief ability suppresses this ordinary branch; its ejection behaviour is outside this space slice. Flyout geometry uses the loaded model frame and bounds under the existing simulation geometry conventions. The first bone/distance values are consumed here only for destruction survivors; other consumers of those list tags retain their own coverage gaps.

Birth work is confined to the admitted companies. Placement reads the existing spatial collection and a sparse same-tick birth overlay. There is no new world scan or periodic serial entity pass. Newborn rows join by ordered insertion after indexed services, and participate in ordinary final publication and lifecycle notifications.

Non-flying companies create their authored bodies and optional teams, and the initial flyout reaches the physical members. Later orders addressed to a non-flying team container still await the existing Container team dispatch work tracked by [TCFA-04](tag-coverage-fighters-ai.md). This downstream gap does not prevent survivor creation or initial flyout. Unteamed non-flying members retain ordinary body command routing.
