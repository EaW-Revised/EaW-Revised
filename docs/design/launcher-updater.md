# Launcher updater and installer design

Status: research and proposed design for the launcher updater. The four implementation steps below are backlog work; no updater or signed update feed is claimed to exist yet.

## Goal and boundaries

Let a player check for a release, read its notes, explicitly download and install it, or install from a launcher-only bootstrap. Keep the previous version runnable and offer rollback. Stable is the default; preview is opt-in. This is a consumer of releases, never a publisher. Builds stay local, with zero new hosted CI minutes, no publication without the owner's explicit approval, and no code-signing certificate (owner decision (legacy EAWR-3966)). The launcher is GPL-3.0-or-later; dependencies must be compatible and their notices shipped. No elevation, telemetry, hard-coded mod lists, or edits to players' mods or Workshop copies. The Steam game folder is untouched except existing documented mod/layer folders; the proposed updater does not need to write even those. Account for free disk space and a user-selected writable install directory.

## Evidence and current contracts

- `docs/releasing.md` describes locally built, manually approved draft assets, fresh-user checks and checksums. Its release-status paragraph says 0.2.7, but the public release list shows 0.3.1; treat that paragraph as stale, not as feed truth.
- `tools/release/package_release.py` makes a single top-level player directory in the zip and writes folder `SHA256SUMS` as lowercase SHA-256, two spaces, relative slash path, newline. Archive `SHA256SUMS.txt` uses digest, two spaces, archive filename. Public 0.3.0 and 0.3.1 assets have separate Windows Debug sums; 0.3.1 also has Linux sums. Their filenames differ in whether the version includes `v`, so select the exact manifest asset name, not a synthesized name. These sums alone are not authenticated.
- The player/Debug layer is `<player>/Revised/Data`; `tools/release/package_release.py` requires it unless explicitly allowed missing and `--public` refuses a configured layer. `tools/release/add_revised_layer.py` can add it locally, rebuild sums and replace the zip; sign only the final resulting bytes. `tools/release/pool_host/Package-OnHost.ps1` passes the layer, public and missing-layer options to the packager.
- `config/launcher-pin.json` pins manager 0.1.11 by artifact digest and protocol floor at this base. The manager artifact is bundled as `launcher/` with its matching service; `apps/launcher/README.md` and the launcher repository's `README.md` describe the native `EAWR.exe`, `EAWR Mods.exe`, Godot `project/`, `project/src/manager/`, service client and tests. The launcher repository currently reports 0.1.13; that does not change the game package's pin.
- `package_release.py` verifies binary build identity against `--expect-identity`; `runtime.json` records schema, variant, Godot identity and component hashes, **not the game commit/build ID**. A signed manifest must add the exact game build identity from the verified build provenance; do not infer it from `godot_identity`. The service hello exposes `engine_build` (`docs/mods-service-protocol.md` and launcher `project/src/service/mods_service_client.gd`); its exact equality to the future release manifest identity must be verified in implementation.
- `apps/launcher/README.md` defines stay-open requests, `game-running.json` with PID and optional process creation time, and `launch-result.json`. The manager can stay open while the game runs. Pending, running, malformed or indeterminate states must block activation and deletion; PID alone is insufficient because of reuse. This contract is evidence for coordination, not a guarantee that every separately started game process is tracked.

## Feed, manifest and consent

Use public GitHub Releases over HTTPS, read-only: `GET /repos/EaW-Revised/EaW-Revised/releases`, paginating as necessary. Published releases are visible unauthenticated; drafts are not. [GitHub's release API](https://docs.github.com/en/rest/releases/releases) and [rate-limit guidance](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) define the interface. Use a serial, infrequent check, bounded response sizes, cached ETag and conditional requests; do not assume unauthenticated 304s are free of quota. Honor `Retry-After` or reset headers on 403/429 and back off. Offline, rate-limited, missing manifest or invalid signature means a clear status and continued local play, never an unverified install. An explicit manual check remains available; disabling the automatic check stops its requests. An HTTPS request exposes ordinary network metadata to GitHub, but sends no telemetry, credentials, mod names or paths.

Filter the returned release objects for `prerelease == false` for stable; preview opt-in may include both channels. Treat release-list data as discovery only: require signed channel and release tag to agree with the listing. Order candidates by signed monotonic sequence, not API ordering or lexicographic tag. Display only signed release notes as update claims, with safe plain-text rendering. No background download: the player clicks **Update**, sees version, notes and size, and consents before transfer. Show installed and candidate build IDs. Lobby UI must compare host and local game build IDs, warn on mismatch and link to the update screen; where lobby identity plumbing is absent, add it in the relevant game and launcher work and do not claim an existing warning.

The launcher repository already produces its own `manifest.json` and `zip.sha256` for its launcher artifact. Keep these as existing launcher packaging metadata and checksum, not update-feed authority: the game release feed has exactly one authoritative signed `update-manifest.json`, covering the complete game archive including the bundled launcher. Do not merge the two formats or infer trust from the unsigned launcher files; verify consistency with the bundled artifact as part of packaging. Proposed `update-manifest.json` and detached `update-manifest.json.minisig` are release assets beside existing archives and sums. The signature covers the exact UTF-8 bytes, verified before parsing; specify duplicate-key rejection, strict schema and limits. Schema 1 contains project and schema IDs, release tag, channel, monotonically increasing integer sequence, game build ID, minimum bootstrap/launcher version, notes as plain text, and an array of exact archive asset names, platform, variant, byte size and SHA-256. Match precisely one Windows player asset; reject duplicate names, unexpected fields where security relevant, invalid size/hash, mismatched release/channel, unsupported schema or incompatible minimum version. URLs are derived from the matching release asset, restricted to HTTPS, with at most five redirects and an explicit host allowlist of `github.com` and `release-assets.githubusercontent.com` for asset downloads; fail closed on unknown hosts and revalidate the list against the release flow before shipping; never interpret arbitrary signed strings as local paths. The manifest's signed archive hash covers the full archive, including the manager, service and Revised layer, not merely internal sums.

Release follow-up: after packaging and any layer addition, calculate sizes/digests from the final archives and build identity from verified provenance, create and owner-sign the manifest locally, upload both assets with the existing files to the draft, download and verify those exact bytes, then publish only on owner approval. Every reissue, including a rebuild of the same tag, receives a new sequence; prefer a new tag and require the signed tag to match the listing. Existing unsigned releases remain manually downloadable; they cannot be silently promoted to trusted updates. Signed manifest creation and runbook changes require a separate game-repo PR and owner's key decision.

## Trust and threats

Recommend minisign's Ed25519 prehashed format and detached signature, with the public key embedded in the bootstrap; its [format specification](https://jedisct1.github.io/minisign/) defines the signed bytes and key ID. Compared with a raw Ed25519 protocol it supplies an established interoperable format; OpenPGP adds more key and parsing machinery, while a code-signing certificate is outside the owner's decision. Use the ISC-licensed minisign verification format and libsodium primitives; validate the integration and transitive licences at the Godot/native boundary. Require prehashed signatures: upstream minisign accepts legacy signatures by default, so enforce the equivalent of its `-H` option. Prefer a small native verifier shared by bootstrap and install path, with test vectors, rather than custom cryptography. Owner alone controls an encrypted offline signing key and backup; no key in repository, build pool or hosted CI. Embed public keys and IDs in the trusted bootstrap. Planned rotation: ship an update trusting old and new keys signed by the old key, then sign with the new key and eventually remove the old key in a later trusted update. If the old key is compromised, that chain is insufficient: stop updates and distribute a replacement bootstrap through an independently authenticated owner-approved channel. Signing cannot protect against compromised signing keys, malicious owner-signed builds, a compromised local machine, denial of service, or a first bootstrap obtained from an untrusted source. Signed archives execute unsandboxed with the user’s rights. Updater-written unsigned executables may lack Mark-of-the-Web and bypass the normal SmartScreen prompt; the owner must choose a visible equivalent warning or a verified marking policy before release.

| Threat | Required handling and limit |
| --- | --- |
| Tampered transfer | Verify signature then full archive size and SHA-256; fail closed. HTTPS also protects transport. |
| Hijacked release account | Cannot forge a manifest without signing key; can withhold updates or replay old signed ones. |
| Downgrade/rollback | Persist highest accepted signed sequence per channel outside version folders; reject lower/equal conflicting metadata. Explicit local N-1 rollback is separate and does not lower the watermark; it deliberately permits running a potentially vulnerable older build. First install, deleted state or restored backups cannot prove freshness; signed expiry needs a trustworthy clock and is an owner decision. |
| Zip slip or hostile archive | Reject absolute, drive, UNC, `..`, alternate streams, links/reparse points, duplicate/case-colliding paths and unexpected top-level layout; bound expanded bytes/count and extract only into a new controlled directory. |
| Partial download | Keep partial separately, validate range response and identity before resume, otherwise restart; never activate until complete hash passes. |
| Malicious manifest | Verify signature before strict bounded parsing, reject malformed or unsupported data; signed malicious metadata from a compromised key remains trusted. |
| TOCTOU swap | Restrict staging to the user's private directory; hash an open handle and extract from those same verified bytes/handle, prevent concurrent replacement where supported, revalidate before activation; local same-user compromise is outside the guarantee. |

## Installation and recovery

Proposed root contains a stable bootstrap entry point backed by a versioned selector, `versions/<build-id>/` with each complete extracted player folder, a small current pointer, previous pointer and private staging. IDs are validated opaque names, never paths. The bootstrap resolves a validated pointer and starts that version. Stage on the same filesystem, verify and fully extract before flushing files and atomically replacing the pointer with a same-directory temporary file; retain the former pointer as N-1. A journal and startup recovery resolve crashes before/after the switch, preserve a runnable old version and reject incomplete stages. On Windows evaluate `ReplaceFileW` or `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING` for same-directory selector replacement; their crash atomicity is not established by this design. Probe supported filesystems and inject termination and power-loss failures at each transition; if the required guarantee cannot be established, disable activation and leave the old version selected. The engine/platform team must decide and prove the primitive and durability contract before implementation ships. Keep old files while any tracked game or launcher uses them, and never assume a missing state file proves no separately started process exists: hold a named mutex or exclusive user-data lock across each managed launcher/game lifetime, and defer cleanup if exclusivity cannot be proved. Separately launched processes remain an unresolved engine integration decision. Switch only after pending/running games and manager instances exit; ambiguous state requires the player to close them. Downloads may be staged with consent while running but cannot activate then. A failed new start offers an explicit rollback; retain N-1 until the new version is confirmed working and rollback is no longer needed. Free space failures, cancellation and crashes leave the previous version intact.

First run: a separately distributed, owner-approved launcher-only bootstrap includes its own trusted key, networking and verifier; choose a writable install folder, then use the same signed-manifest, consent, download and staging flow. The current manager project depends on a Godot runtime and service, so the existing manager zip alone is not a verified standalone installer. Bootstrap packaging and its distribution are new work.

The stable entry point is a versioned, independently recoverable bootstrap selector, not an unchanging executable. The bootstrap verifies the helper bytes against the signed package before execution; the helper waits for the bootstrap and managed processes to exit. The bootstrap cannot overwrite a running Windows executable. Stage a verified replacement and have the helper switch the versioned bootstrap selector, retaining the previous version for recovery, then restart. A running NTFS executable may be renamed but cannot be assumed deletable while in use; do not depend on that behavior for the selector. `MOVEFILE_DELAY_UNTIL_REBOOT` requires privileged registry access and is excluded. The helper itself must be versioned or separately replaceable on a later start, and authenticated as part of the signed package. Test interrupted swap and locked files; avoid a single self-replacing executable as the sole recovery path. Profiles, saves and settings must live outside `versions/` in the existing stable Godot user-data location; preserve the existing viewer and service paths and verify overrides end to end (manager `--user-data` forwarding is not yet supported). Version cleanup is confined to updater-owned directories. Saved profile layer roots are absolute and the engine first uses an existing root, re-resolving by key only when missing; retaining N-1 means the old root may still exist. The engine must add a version-aware remap or equivalent validated re-resolution for managed bundled layers before switching, and test both switch and rollback without rewriting external mod roots. The derived `builtin:revised` layer also needs discovery against the selected version; its exact engine integration is an open decision. Each version's bundled `Revised/Data` travels with that package; never move, overwrite or delete external mods or Workshop items.

Disk planning must use actual archive size plus expanded size, retained current and N-1 trees, staging and filesystem overhead, not a zip-only multiplier. The 0.3.1 Windows player zip is 113,190,745 bytes (about 108 MiB); even three such compressed archives would be about 324 MiB before extracted trees. Check free space against measured sizes and fail before changing the selector.

## Reuse map

These are proposed dependencies or patterns, not evidence of completed integration. Licence compatibility is preliminary; inspect each file and transitive dependency before distribution. Preserve required copyright and licence notices for MIT, ISC, BSD and curl-licensed material. MPL-2.0 files require their original notices, source distribution obligations and a `THIRD_PARTY_NOTICES.md` provenance entry **before the file lands**; verify secondary-licence eligibility. GPL-3.0-or-later fits the project licence, subject to its source and notice duties and the project's clean-room rules.

| --- | --- | --- |
| Signature: libsodium `src/libsodium/include/sodium/crypto_sign.h`; minisign `src/minisign.c` | Link libsodium; use minisign verifier/format, including trusted-comment verification. Integration or a narrowly scoped verifier port needs review; no custom cryptography. | ISC; retain copyright and permission notices. |
| Download and hash: curl `include/curl/curl.h`; libsodium `src/libsodium/include/sodium/crypto_hash_sha256.h` | Link curl for HTTPS/resume and libsodium for SHA-256; rehash all bytes and validate range/identity. | curl permission licence and ISC; retain their notices. |
| Switch/recovery: Velopack `src/bins/src/commands/apply_windows_impl.rs` | Rebuild the selector; use backup/restore recovery as a pattern only, not a code port. | Stub: Velopack `src/bins/src/commands/start_windows_impl.rs`; MO2 `src/selfupdater.cpp` | Velopack is a helper/start/wait/restart pattern; MO2 hands off to an external installer with a destination argument and quits on successful launch. The minisign source vendors `src/libzodium`; trace that copy’s provenance and obligations before taking code from it. Upstream licence texts were checked in read-only shallow clones; nested dependencies and file provenance still require review. MPL and BSD are included as intake rules, not claimed updater dependencies.

## Delivery order and estimates

Worker-hours are active engineering time, including implementation, feature tests and fix cycles. The raw estimate is the planning basis: **68–112 worker-hours**, or **8.5–14 eight-hour working days** for one uninterrupted worker. Owner decisions and availability can extend elapsed time.

For context, a snapshot of all 22 merged launcher-repository PRs has open-to-merge median 20.1 minutes and nearest-rank p80 83.5 minutes. A separate sample of 10 merged game-repository mod service and manager PRs (legacy EAWR-5020, EAWR-5035, EAWR-5039, EAWR-5050, EAWR-5060, EAWR-5436, EAWR-5439, EAWR-5444, EAWR-5455, EAWR-5480) has median 101.6 minutes and p80 116.5 minutes. These populations differ in scope; both windows include review and queue waits but exclude work before PR opening. Available coordination notes do not consistently record both dispatch and PR READY times, so they do not support a reliable worker-hour distribution.

The comparison formula is **9 PRs × 20.1–116.5 minutes = 3.0–17.5 hours open-to-merge**, where the low end is the launcher-repo median (20.1 min, 22 PRs) and the high end is the game-repo service/manager p80 (116.5 min, 10 PRs): two different populations, shown as one comparison window. It is a LOWER bound that excludes all worker time before a PR opens (spec, build, tests), and it is not a forecast of total work. Do not add that window to the raw estimate: its review and fix cycles can overlap the raw worker-hours, and both inputs omit or handle waits differently. The security, platform, signing and fault-injection work makes the raw range more appropriate for planning. Independent work can overlap where dependencies permit.

| Order / work | PR count | Raw worker-hours (planning basis) | Open-to-merge comparison (20.1–116.5 min per PR) |
| --- | ---: | ---: | ---: |
| 1. Check, signed notes, verifier and lobby identity seam | 2 | 8–12 | 0.7–3.9 h |
| 2. Download, resume, SHA-256 and release-manifest tooling | 2 | 16–24 | 0.7–3.9 h |
| 3. Install, profile integration, fault injection and rollback | 2 | 24–40 | 0.7–3.9 h |
| 4. Bootstrap self-update and recovery | 1 | 12–20 | 0.3–1.9 h |
| Bootstrap packaging and first-run distribution | 1 | 4–8 | 0.3–1.9 h |
| Owner key ceremony, signing and release runbook | 1 | 4–8 | 0.3–1.9 h |
| **Total** | **9** | **68–112** | **3.0–17.5 h** |

PR1 tests signature vectors, mock pagination, caching, channels and signed notes; PR2 tests resume and final archive integrity; PR3 tests extraction, locks, profile remapping and crash recovery; PR4 tests helper verification and interrupted replacement. Bootstrap packaging and the signing runbook each need their own review. This ordering is a proposed decomposition, not proof that nine PRs will suffice.

The raw estimate includes signing ceremony and owner key custody coordination, platform testing and rollback fault injection that the PR-open window cannot measure. The estimates are not commitments.

## Owner decisions

1. **Check policy:** automatic check on startup with opt-out, or manual-only? Recommend startup check with visible opt-out and no background download.
2. **Trust and freshness:** owner-only minisign key with monotonic watermark, or a more elaborate signed metadata system with expiration? Recommend minisign plus watermark initially; accept first-install/clock limitations and revisit expiry.
3. **First-run distribution:** publish a dedicated native bootstrap or require a full player zip first? Recommend dedicated signed-manifest-verifying bootstrap, distributed only after explicit approval; it remains an unsigned executable.
4. **Migration and switch:** migrate existing portable folders into managed versions, or ask for a new managed folder? Recommend a new folder first; preserve the original portable install and never mutate it during migration.
5. **Preview:** opt-in prereleases alongside stable, or stable only until a preview exists? Recommend opt-in, with signed channel binding and independent sequence watermarks.
6. **Rollback retention:** retain exactly N-1, or retain more configurable versions? Recommend N-1 with explicit rollback and no automatic deletion of a running version.
7. **Bootstrap update:** staged helper swap, or defer bootstrap replacement until the next manual launch? Recommend staged helper with recovery and player-visible restart; defer when files are locked.
8. **Windows warning:** show an explicit unsigned-executable warning or establish a verified Mark-of-the-Web policy? Recommend a visible warning until the marking behavior is tested.
9. **Engine integration:** select and prove the durable selector primitive, process locks, version-aware profile-root remapping and bundled-layer discovery before activation; separately launched games require an agreed detection or cleanup policy.
