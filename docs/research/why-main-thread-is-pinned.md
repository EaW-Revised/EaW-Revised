# Why the viewer main thread is overloaded

Safe puts Godot drawing, BVH and dirty-instance maintenance inline on main: roughly half its sampled work.
EAWR presentation outside renderer glue is roughly a quarter; driver work is about a tenth (coarse attribution).
On Jerre i5-12450H / RTX 4060 / 16 GB, **RED diagnostic** Separate halves main CPU seconds but shifts load to a busy engine worker candidate.
Safe/Separate native medians are 125.941/84.0355 ms; total captured CPU is 78.3/124.4 seconds in later approximately 60-second windows.
Image, shutdown and measurement errors remain: **No validated production speedup is established.**

2026-10-23. The main thread combines presentation work with Godot rendering in Safe mode. Separate shifts work to another thread and records shorter native intervals, but correctness gates fail. **No validated production speedup is established.**

**Execution policy.** The project leaves Godot's thread model at its Safe default. `RenderingServerDefault::draw` runs `_draw` inline: scene/spatial updates, particles, viewport drawing and CPU command submission share main with EAWR presentation. Simulation/pose workers cannot move that engine work themselves. The pinned [startup policy](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/main/main.cpp#L2776) and [draw implementation](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/rendering_server_default.cpp#L443) establish this route; unresolved stacks alone do not identify a particular subsystem.

**Matched query-free diagnostic, strict RED.** Jerre RTX 4060 Laptop, stock Godot 4.7.2, c4 viewer DLL `7c014876...a90d9`; both cells budget OFF, native/observer timing queries OFF, counters OFF, caps/vsync 0. Native ticks 1200–3500 supply 4,602 rows per mode. These are native frame intervals, not displayed-frame times.

CPU samples occur after native 3600, separately from the wall window. All 65/67 captured TIDs are retained. Separate's largest non-main TID 15572 consumes 54.984 CPU seconds; stock engine symbols do not prove its exact function/role. Main busy-stack shares move from 43.2% unresolved Godot, 19.1% renderer glue and 13.2% particles in Safe to 46.5% particles, 14.1% renderer glue, 13.4% pose and 12.0% presentation synchronization in Separate. Only 220/142 main busy observations underpin those estimates. Categories are sampled attribution, not independent timers; inclusive API costs overlap them. Per-callback normalization is not completed-render-frame normalization when engine IDs repeat.

Total captured CPU rises about 59%, while the earlier native median interval is about 33% shorter. Separate also delivers 52% more callbacks in its sampler window; total CPU per callback rises about 4.6%, so the 59% increase is not a 59% per-frame overhead claim. Windows differ, and callback counts do not establish displayed frames or CPU energy per frame; higher aggregate demand still matters for weaker CPUs. TID 15572 uses 91.4% of one core and is busy in 305/313 observations, rather than mostly parked in idle waits. Unresolved stock-engine frames cannot distinguish productive rendering from active spinning; it is a render-worker candidate, not a proven thread identity. Short-lived/inaccessible threads can be absent from the sampler total.

Hardware: Jerre is i5-12450H, 12 logical threads, 16 GB RAM, RTX 4060 Laptop; the symbol control is a laptop build host, i7-14700HX, 16 GB RAM, RTX 4070 Laptop. These are separate hosts and engine/compiler configurations.

Both runs exit 0, complete 4801 native ticks, share start identity `441da1c0...3050` and final state `c2f30043...12d96`. Exact-source, lossless collector, budget-off, uncapped, PNG/hash/dimension and four host-memory guards pass; free RAM stays 10.42–10.73 GB. Task and queue release pass. Four viewed startup/final PNGs show closely matched populated fleets, combat, HUD and minimap. This does not prove pixel parity or exact requested rendered ticks.

Godot's [shutdown finalization issue](https://github.com/godotengine/godot/issues/119000), [Separate exit crash](https://github.com/godotengine/godot/issues/124799) and open [ownership restoration patch](https://github.com/godotengine/godot/pull/123391) match the quit source path and minimal reproduction with two leaks. The render worker owns RD; shutdown joins it and deletes RD on main without restoring ownership. Upstream reports include cache-persistence failure and an exit crash. No engine patch is authorized.

**Render progress is bounded, display progress unmeasured.** Full-run post-draw counts are 9,631/9,630. Godot [synchronizes the command queue before each new draw](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/main/main.cpp#L5074), preventing an indefinitely growing CPU render backlog. Post-draw callbacks follow CPU `end_frame` but arrive deferred; `Engine.frames_drawn` increments on enqueue in Separate. Neither proves GPU completion or display cadence. Process/swapchain-scoped external presentation tracing remains unqualified. A completed no-ETW proof establishes the private Python collector → Godot console → GUI chain; the final selector targets only the GUI and records non-Godot helper children. The final authorized PresentMon 2.6.0 attempt launched, but Windows denied starting the trace session: the account needs administrative privileges or Performance Log Users membership. No permissions were changed; retries stopped. The owner permission question defaults to making no change without an answer. No present CSV, cap-response comparison, event-quality coverage, display cadence or input latency was obtained. Task removal, queue release, zero remaining private-run processes and absence of the unique ETW session were verified.

The logging-only case uses isolated source `0e92ff26`, DLL `379ccde6...4cba`, Separate mode, budget/query/counters OFF and caps/vsync 0. Native 61-tick completion, final identity `bef88e19...18f`, source/collector/capture checks, before/after memory guards and task/queue cleanup pass. Zero forced-sync warnings were logged. The two startup image errors, quit error/leaks and duplicate/gapped observer IDs keep it **strict RED**; it is not a performance benchmark. Neighboring native-context markers are not exact error ticks or caller/order proof.

**Named engine causes, separate control.** The optimized MSVC symbol engine on a laptop build host with an RTX 4070 Laptop resolves all 296 engine-leaf observations: main 87.88 CPU ms/frame, engine leaves 50.22. Largest leaves are vertex-array binding 4.41, command-graph insertion 2.88, DynamicBVH updating 2.88, Vulkan offsets 2.54 and dirty-instance updates 2.21. Inclusive `_draw` 42.08 and `free_rid` 9.84 overlap those leaves. This establishes submission/spatial maintenance work; different hardware/compiler/window prevents transferring its milliseconds to Jerre or claiming stock-engine savings.

**Other levers and limits.** Earlier GTX reuse activated but median worsened 153.36→154.15 ms. Halving casters removed 2,495 shadow draws and saved 5.33 ms while changing output; it cannot ship. All pre-recycle GTX timings are possibly memory-pressure contaminated. The first query-free Jerre run was also invalidated by our orphaned monitoring readers consuming about 15 GB; they were removed and readers now use bounded I/O and self-watchdogs. Existing authored LOD1/2 alternatives number zero across 157 surveyed model paths, so existing LOD savings are zero. Hull/hardpoint grouping remains unimplemented; no grouping gain follows from the caster mask.

The owner's separate RX 7900 XTX Dev4 CSV has a precombat floor 12.636 wall/9.654 viewer ms at 166.5 draws and 74 units. Combat median/p99 are 32.600/74.127 ms with 0.840 GPU ms. Slow rows increase previous-frame viewer time and current outside time; current profiles do not establish a spike cause or cover the early floor. Texture first use and retirement remain candidates. Heavy Remake memory qualification, capture ordering and input latency remain open.
